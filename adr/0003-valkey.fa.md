# ADR-0003: Valkey برای شمارنده‌ها، cache و pub/sub

- **Status:** Accepted
- **تاریخ:** 2026-11-07
- **تصمیم‌گیرندگان:** تیم DiRouter

## زمینه

replicaهای gateway به یک دید مشترک از RPM، TPM، همزمانی، مصرف زندهٔ بودجه، وضعیت circuit breaker، cooldown اعتبارنامه‌ها و قفل مدل‌ها نیاز دارند. تغییرات پیکربندی باید سریع به همه gatewayها برسد. عملیات باید اتمی باشند و هدف تأخیر زیر یک میلی‌ثانیه داشته باشند؛ PostgreSQL برای این بار کاری مسیر پرترافیک انتخاب نشده است.

### عوامل تصمیم

- عملیات Lua اتمی چندمرحله‌ای برای محدودیت‌های sliding-window یا GCRA.
- هدف تأخیر زیر ۱ میلی‌ثانیه.
- اعلان‌های پیکربندی با pub/sub.
- مجوز باز با ریسک کمتر تغییر مجوز.
- سازگاری با کتابخانه‌های موجود، از جمله ioredis و BullMQ.

### گزینه‌های بررسی‌شده

1. Valkey.
2. Redis 8.
3. شمارنده‌های حافظه‌ای جدا برای هر gateway با سهمیه‌های تقسیم‌شده بین گره‌ها.
4. NATS JetStream KV.

## تصمیم

از **Valkey** استفاده شود؛ فورک BSD-licensed از Redis که با RESP سازگار است و از طریق `ioredis` به کار می‌رود.

- محدودیت‌های نرخ و بودجه با اسکریپت‌های Lua اتمی و کلیدهای با انقضا اعمال می‌شوند.
- اعلان نسخه snapshot روی `config:changed` منتشر می‌شود.
- وضعیت breaker و cooldown با استفاده از TTL بین replicaها به اشتراک گذاشته می‌شود.
- **fallback محلی:** اگر Valkey در دسترس نباشد، از یک محدودکننده حافظه‌ای با سهمیه‌های تقسیم‌شده بین گره‌ها استفاده می‌شود. `failMode` (`open` یا `closed`) رفتار هنگام خرابی را تعیین می‌کند.

## پیامدها

### مثبت

- یک جزء، شمارنده‌ها، cache، pub/sub و صف را مدیریت می‌کند (ADR-005).
- مجوز BSD و سازگاری با پروتکل Redis با ابزارهای انتخاب‌شده هم‌خوان است.
- مسیر HA، Sentinel یا Cluster است.

### منفی

- Valkey یک وابستگی زمان اجرا اضافه می‌کند؛ fallback محلی دقیق‌تر نیست و ممکن است مقداری عبور از سقف مجاز را بپذیرد.
- شمارنده‌ها در حافظه نگه داشته می‌شوند. مصرف بودجه باید به‌صورت دوره‌ای با دفتر مالی PostgreSQL تطبیق داده شود.

### پیگیری

- پیاده‌سازی‌های محدودکننده نرخ توزیع‌شده و بودجه، جزئیات الگوریتم را تعریف می‌کنند.
