# ADR-0007: وضعیت فایل‌ها، batchها و تسک‌های async در Valkey است و گیت‌وی آن را پیش می‌برد

- **وضعیت:** پذیرفته‌شده
- **تاریخ:** 2026-11-25
- **تصمیم‌گیرندگان:** تیم DiRouter

## زمینه

تا اسپرینت ۵ هر درخواست data plane در یک تبادل HTTP تمام می‌شد. Files و Batch API (کارت ۳۰.۱) و تسک‌های async مثل تولید ویدیو (کارت ۳۰.۶) اولین endpointهایی هستند که وضعیتشان از خود درخواست بیشتر عمر می‌کند: فایل چند روز نگه داشته می‌شود، batch تا ۲۴ ساعت نزد provider اجرا می‌شود، ویدیو چند دقیقه، و webhook باید بعد از خطا دوباره فرستاده شود. چیزی باید این وضعیت را نگه دارد، provider را تا پایان کار دنبال کند، و usage و تسویهٔ کیف پول را دقیقاً یک بار ثبت کند.

### عوامل تصمیم

- ADR-0006: گیت‌وی برای ترافیک به control-api یا Postgres وابسته نیست و فقط گیت‌وی `MASTER_KEY` را دارد، پس فقط او می‌تواند credentialهای provider را رمزگشایی کند.
- چند replica گیت‌وی به یک سازمان خدمت می‌دهند و هر کدام ممکن است `GET /v1/batches/{id}` بعدی را بگیرد.
- usage هر batch یا تسک یک بار و هنگام پایان ثبت می‌شود، حتی اگر replica وسط کار از کار بیفتد.

### گزینه‌های بررسی‌شده

1. رکوردها در Postgres از طریق control-api؛ worker وضعیت provider را می‌پرسد.
2. رکوردها در Valkey؛ worker وضعیت provider را می‌پرسد.
3. رکوردها در Valkey؛ یک job poller داخل هر replica گیت‌وی وضعیت provider را می‌پرسد، با قفل جداگانه برای هر مورد.

## تصمیم

گزینهٔ ۳.

- رکورد فایل، batch، تسک و ارسال webhook یک مقدار JSON با TTL در Valkey است (`dirouter:jobs:<kind>:<id>`) و فهرست هر سازمان با یک sorted set نگه داشته می‌شود؛ بدون Valkey (یک گره محلی) همین store در حافظه اجرا می‌شود.
- بایت‌های فایل در object store است نه Valkey: یک volume محلی یا باکت سازگار با S3 (`FILES_STORAGE`).
- کاری که بعداً باید انجام شود (بررسی batch یا تسک نزد provider، تلاش دوبارهٔ webhook، حذف فایل منقضی) در یک sorted set بر اساس زمان سررسید است. poller هر replica موارد سررسیدشده را برمی‌دارد و هر کدام را قفل می‌کند (`SET NX PX`)، پس replicaها کار را تقسیم می‌کنند و هیچ کاری دو بار اجرا نمی‌شود؛ اگر replica از کار بیفتد قفلش منقضی می‌شود. مشتری‌ای که job را دریافت می‌کند هم آن را تازه می‌کند.
- پایان job (کپی نتایج، رویداد usage با شناسهٔ job به‌عنوان کلید idempotency، تسویهٔ کیف پول) زیر قفل انجام و در خود job ثبت می‌شود، پس یک بار رخ می‌دهد.
- گزینهٔ ۲ رد شد چون worker به `MASTER_KEY` و credentialهای provider نیاز پیدا می‌کرد که ADR-0006 فقط در گیت‌وی نگه می‌دارد؛ گزینهٔ ۱ علاوه بر آن control-api را سر راه هر قدم job می‌گذارد.

## پیامدها

### مثبت

- data plane در قطعی control plane مثل بقیهٔ درخواست‌ها کار می‌کند.
- سرویس تازه‌ای لازم نیست: poller یک حلقهٔ کوچک در پردازه‌ای است که credentialها، محافظ SSRF و پروکسی‌های خروجی را از قبل دارد.
- usage و صورت‌حساب از همان صف usage می‌گذرند و ledger تغییری نمی‌خواهد.

### منفی

- رکوردهای job در Postgres نیستند: با SQL قابل پرس‌وجو نیستند و اگر Valkey داده‌اش را از دست بدهد از بین می‌روند (persistence در Valkey باید روشن باشد، که در Compose و Helm هست).
- poller کمی بار پس‌زمینه به گیت‌وی اضافه می‌کند (یک خواندن sorted set در ثانیه برای هر replica).
- `FILES_STORAGE` محلی فقط با یک replica یا volume مشترک کار می‌کند؛ راه‌اندازی HA به S3 نیاز دارد.

### پیگیری

- کارت ۳۰.۱ (فایل‌ها و batch) و کارت ۳۰.۶ (تسک‌های async و webhook).
