# احراز هویت داشبورد، نشست‌ها، توکن‌های مدیریتی و ویزارد راه‌اندازی

کد: `apps/control-api/src/auth` · تست: `auth.unit.test.ts` و `auth.integration.test.ts` · کارت ۳.۴

## endpointها (`/api/v1/auth`)

| مسیر                        | توضیح                                                                                                                                                         |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /setup`                | `{"required": true}` تا وقتی هیچ کاربری نیست                                                                                                                  |
| `POST /setup`               | `{organizationName, name, email, password}`: سازمان، کاربر و عضویت OWNER را می‌سازد و وارد می‌شود. بعد از اولین کاربر همیشه **409 `setup_completed`** می‌دهد. |
| `POST /login`               | `{email, password}`: پاسخ access token است و refresh token در کوکی می‌رود                                                                                     |
| `POST /refresh`             | با کوکی: توکن را می‌چرخاند و access تازه می‌دهد                                                                                                               |
| `POST /logout`              | خانوادهٔ نشست را باطل می‌کند و کوکی را پاک می‌کند (204)                                                                                                       |
| `POST /password`            | با Bearer: `{currentPassword, newPassword}`؛ همهٔ refresh tokenهای کاربر باطل می‌شوند (204)                                                                   |
| `GET /me`                   | با Bearer: کاربر (با `emailVerified`) و سازمان‌ها با نقش                                                                                                      |
| `GET /sessions`             | با Bearer: نشست‌های فعال کاربر (بخش «نشست‌ها» در پایین)                                                                                                       |
| `DELETE /sessions/{id}`     | با Bearer: یک نشست کاربر را می‌بندد (204؛ اگر مال او نباشد یا تمام شده باشد 404)                                                                              |
| `POST /sessions/revoke-all` | با Bearer: `{includeCurrent?: false}`؛ از همهٔ نشست‌های دیگر، یا با همین نشست از همه‌جا، خارج می‌کند                                                          |

همه در Swagger (`/api/docs`) با اسکیمای کامل از zod هستند. خطاها با قالب `application/problem+json` و کد پایدار برمی‌گردند.

## رمز عبور

- **argon2id** (`@node-rs/argon2`، باینری از پیش ساخته برای linux-musl/arm64/x64) با پارامترهای OWASP: m=19MiB، t=2 و p=1.
- رمز حداقل ۱۰ و حداکثر ۲۵۶ کاراکتر است. سقف جلوی DoS روی argon2 را می‌گیرد.
- ایمیل با حروف کوچک ذخیره و مقایسه می‌شود.
- برای ایمیل ناموجود هم یک verify روی hash ثابت انجام می‌شود و پاسخ همان `invalid_credentials` است. پس نه زمان پاسخ و نه پیام وجود حساب را لو نمی‌دهند.

## توکن‌ها

|       | access token                                                                  | refresh token                                                                   |
| ----- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| قالب  | JWT HS256 (`jose`) با `JWT_SECRET`، iss `dirouter` و aud `dirouter-dashboard` | ۳۲ بایت تصادفی (base64url)                                                      |
| عمر   | ۱۵ دقیقه                                                                      | ۳۰ روز                                                                          |
| کجا   | بدنهٔ پاسخ؛ داشبورد آن را در حافظه نگه می‌دارد، نه localStorage               | کوکی `dr_refresh`: `HttpOnly`، `Secure`، `SameSite=Strict`، `Path=/api/v1/auth` |
| در DB | —                                                                             | فقط `HMAC-SHA256(JWT_SECRET, token)` در `refresh_tokens.token_hash`             |

### چرخش و تشخیص سرقت

هر ورود یک **خانواده** (`family_id`) می‌سازد. هر `refresh`:

1. توکن را پیدا می‌کند. اگر `used_at` یا `revoked_at` داشته باشد، یعنی توکن قبلاً مصرف شده (کسی کپی‌اش را دارد). **کل خانواده باطل می‌شود** و پاسخ 401 `refresh_token_reused` است. پس مهاجم و کاربر واقعی هر دو بیرون می‌افتند و کاربر باید دوباره وارد شود.
2. `UPDATE … SET used_at = now() WHERE id = ? AND used_at IS NULL`. شرط در خود UPDATE است، پس از دو refresh هم‌زمان با یک توکن فقط یکی برنده می‌شود و دیگری به‌عنوان استفادهٔ دوباره رفتار می‌شود.
3. توکن تازه در همان خانواده صادر می‌شود.

تغییر رمز همهٔ refresh tokenهای کاربر را باطل می‌کند.

هر access token نشست خودش (خانوادهٔ refresh token) را در claim `sid` دارد. AccessGuard توکنی را که
نشستش دیگر هیچ refresh token باطل‌نشده‌ای ندارد رد می‌کند؛ پس خروج، تغییر رمز، استفادهٔ دوباره از
refresh token یا بستن نشست، access tokenهای همان نشست را هم در درخواست بعدی‌شان از کار می‌اندازد
(401 `unauthenticated`)، نه این‌که تا ۱۵ دقیقه معتبر بمانند. این بررسی یک جست‌وجوی ایندکس‌دار روی
`refresh_tokens.family_id` است. توکن‌هایی که پیش از این تغییر صادر شده‌اند `sid` ندارند و فقط منقضی
می‌شوند.

## نشست‌ها

کارت ۲۳.۵ · تست: `sessions.integration.test.ts`، `sessions.unit.test.ts` و `sessions-card.test.tsx`
در داشبورد.

هر نشست یک خانوادهٔ refresh token است: با ورود (رمز، passkey، SSO، setup یا پذیرش دعوت) شروع
می‌شود و شناسه‌اش در همهٔ چرخش‌ها ثابت می‌ماند.

| فیلد           | معنا                                                                                |
| -------------- | ----------------------------------------------------------------------------------- |
| `id`           | شناسهٔ خانواده؛ برای `DELETE /auth/sessions/{id}`                                   |
| `device`       | برچسبی از user agent مثل `Firefox on Linux`؛ خود `userAgent` هم برمی‌گردد           |
| `ip`           | نشانی آخرین ورود یا refresh                                                         |
| `createdAt`    | زمان ورود                                                                           |
| `lastActiveAt` | آخرین refresh؛ داشبورد تا وقتی باز است refresh می‌کند، پس این آخرین فعالیت نشست است |
| `method`       | `pwd`، `passkey` یا `sso`                                                           |
| `current`      | برای نشستی که همین درخواست را فرستاده true است                                      |

- بستن یک نشست همهٔ refresh tokenهای خانواده را همان لحظه باطل می‌کند: `POST /auth/refresh` بعدی با
  کوکی آن 401 می‌گیرد و access tokenهایش هم در درخواست بعدی 401 می‌گیرند.
- `POST /auth/sessions/revoke-all` نشست فراخوان را نگه می‌دارد، مگر با `includeCurrent: true`؛ در آن
  حالت کوکی هم پاک می‌شود.
- ادمین: `GET /orgs/{orgId}/members/{userId}/sessions` و
  `POST /orgs/{orgId}/members/{userId}/sessions/revoke` (مجوز `members:write`) نشست‌های یک عضو را
  فهرست می‌کنند و همه را می‌بندند. همان قاعدهٔ تغییر نقش برقرار است: هیچ‌کس نمی‌تواند عضوی با دسترسی
  بیشتر از خودش را خارج کند (ADMIN نمی‌تواند OWNER را خارج کند). نشست‌ها همه‌جا بسته می‌شوند، نه فقط
  در همان سازمان، چون نشست به یک سازمان گره نخورده است.
- audit log: `session.revoked` و `session.revoked_all` (با تعداد نشست‌ها) در همهٔ سازمان‌های کاربر
  ثبت می‌شوند؛ کار ادمین با `member.sessions_revoked` در همان سازمان و با ادمین به‌عنوان actor ثبت
  می‌شود.
- داشبورد: صفحهٔ حساب کاربری نشست‌ها را با «خروج این دستگاه»، «خروج از همهٔ دستگاه‌های دیگر» و
  «خروج از همه‌جا» نشان می‌دهد؛ صفحهٔ سازمان برای کسی که اعضا را مدیریت می‌کند کنار هر عضو دکمهٔ
  «خروج از همه‌جا» دارد.

## توکن‌های API مدیریتی و سرویس‌اکانت

کارت ۲۳.۶ · کد: `apps/control-api/src/service-accounts` و `src/auth/management-token.ts` · تست:
`service-accounts.integration.test.ts`، `management-token.unit.test.ts` و `service-accounts.test.tsx`
در داشبورد.

اتوماسیون (CI، اسکریپت، Terraform) به‌جای نشست کاربر با یک **توکن مدیریتی** API مدیریتی را صدا
می‌زند:

```bash
curl -H "Authorization: Bearer drm_…" https://admin.example.com/api/v1/orgs/<orgId>/keys
```

### سرویس‌اکانت

سرویس‌اکانت یک عضو غیرانسانی یک سازمان است. پشتش یک ردیف کاربر با `is_service_account = true` و
بدون رمز است، پس هرگز نمی‌تواند وارد شود (نه با رمز، نه passkey، نه SSO، نه دعوت)، و یک عضویت که
نقشش (`ADMIN`، `MEMBER` یا `VIEWER`، هرگز `OWNER`) و نقش سفارشی اختیاری را دارد. تغییرهایی که
می‌دهد با خودش به‌عنوان actor در audit log ثبت می‌شوند و منابعی که می‌سازد (کلید، پروژه) سازنده‌شان
همین سرویس‌اکانت است. در فهرست اعضا نمی‌آید و از مسیرهای اعضا قابل تغییر نیست.

| مسیر (`/api/v1/orgs/{orgId}`)        | مجوز             | توضیح                                                                                           |
| ------------------------------------ | ---------------- | ----------------------------------------------------------------------------------------------- |
| `GET /service-accounts`              | `members:read`   | اکانت‌ها با نقش، `permissions` مؤثر و توکن‌ها (هرگز خود توکن)                                   |
| `POST /service-accounts`             | `security:write` | `{name, description?, role, customRoleId?}`                                                     |
| `PATCH /service-accounts/{id}`       | `security:write` | نام، توضیح، نقش یا نقش سفارشی                                                                   |
| `DELETE /service-accounts/{id}`      | `security:write` | عضویت را حذف، همهٔ توکن‌ها را باطل و کاربر پشتش را غیرفعال می‌کند                               |
| `POST /service-accounts/{id}/tokens` | `security:write` | `{name, scopes, expiresInDays?, allowedIps?}`؛ پاسخ `token` را دارد و **فقط همین یک بار** (201) |
| `DELETE /management-tokens/{id}`     | `security:write` | توکن را باطل می‌کند (204)                                                                       |

هیچ‌کس نمی‌تواند به سرویس‌اکانت نقشی بالاتر از نقش خودش یا نقش سفارشی با مجوزی که خودش ندارد بدهد،
یا اکانتی با دسترسی بیشتر از خودش را مدیریت کند (همان قاعدهٔ اعضا، کارت ۱۴.۳).

### توکن‌ها

| ویژگی   | مقدار                                                                                                         |
| ------- | ------------------------------------------------------------------------------------------------------------- |
| قالب    | `drm_` و ۳۲ بایت تصادفی به base64url (۴۷ نویسه)؛ کلید مجازی با `dr-` و توکن SCIM با `scim_` شروع می‌شود       |
| در DB   | فقط SHA-256 توکن در `management_tokens.token_hash` و ۱۲ نویسهٔ اول برای نمایش                                 |
| scope   | مجوزهای ماتریس RBAC ([docs/rbac.fa.md](../rbac.fa.md))؛ توکن فقط‌خواندنی فقط scopeهای `*:read` دارد           |
| انقضا   | `expiresInDays` از ۱ تا ۷۳۰، پیش‌فرض ۹۰؛ `null` یعنی بدون انقضا                                               |
| IP مجاز | `allowedIps` اختیاری: نشانی یا بازهٔ CIDR، IPv4 و IPv6 (`10.0.0.0/8`، `2001:db8::/32`)؛ خالی یعنی از هر نشانی |

هنگام ساخت، هر scope باید هم در نقش سرویس‌اکانت باشد (وگرنه 422) و هم در دسترسی کسی که توکن را
می‌سازد (وگرنه 403).

### بررسی درخواستی که با توکن می‌آید

AccessGuard پیشوند `drm_` را می‌شناسد و توکن را در **هر درخواست** دوباره پیدا می‌کند:

1. توکن ناشناخته، باطل‌شده یا منقضی، یا سرویس‌اکانت حذف‌شده: **401** `unauthenticated`. پس توکن
   باطل‌شده از همان درخواست بعدی رد می‌شود؛ چیزی کش نمی‌شود.
2. نشانی خارج از `allowedIps`: **403**. نشانی همان نشانی کلاینت است که Traefik می‌فرستد.
3. مسیرهای بیرون از `/orgs/{orgId}` (حساب، نشست‌ها، MFA، passkey): **403**. مسیرهای سازمان دیگر:
   **404**، مثل کسی که عضو نیست.
4. OrgGuard: مجوز مسیر باید **هم** در scopeهای توکن و **هم** در نقش فعلی سرویس‌اکانت باشد، پس پایین
   آوردن نقش اکانت توکن‌هایش را همان لحظه محدود می‌کند. سیاست MFA سازمان روی توکن اعمال نمی‌شود.
5. بعضی مسیرها هرگز برای توکن باز نیستند، هر scopeی که داشته باشد (`@HumanOnly()`): مدیریت
   سرویس‌اکانت و توکن، و تأیید یا رد change request (تصمیم با نفر دوم است، کارت ۲۲.۲).

یک تست واحد همهٔ مسیرهای سازمان را می‌گردد و اگر مسیری که چیزی را تغییر می‌دهد (POST، PATCH، PUT،
DELETE) فقط مجوز `:read` بخواهد و برای توکن بسته نباشد شکست می‌خورد؛ دو استثنا (مقایسهٔ playground و
شبیه‌ساز مسیریابی) فقط پاسخی محاسبه می‌کنند و چیزی ذخیره نمی‌کنند.

### audit log

- `service_account.created`، `.updated`، `.deleted`، `management_token.created` (با scopeها، انقضا و
  IP مجاز) و `management_token.revoked`، با شخص به‌عنوان actor.
- `management_token.used` با سرویس‌اکانت به‌عنوان actor، نشانی و `{method, route}`: هر تغییری که با
  توکن انجام شود، و خواندن‌ها دست‌کم ساعتی یک بار برای هر توکن و با هر نشانی تازه. `last_used_at` و
  `last_used_ip` توکن (با دقت دقیقه) به‌روز می‌مانند.
- خود تغییر هم مثل همیشه در مسیر خودش ثبت می‌شود (مثلاً `key.created`) با سرویس‌اکانت به‌عنوان actor.

### داشبورد

صفحهٔ امنیت سرویس‌اکانت‌ها و توکن‌هایشان را نشان می‌دهد (پیشوند، فقط‌خواندنی یا تعداد scope، IP
مجاز، انقضا، آخرین استفاده و نشانی). با `security:write`: ساخت و حذف اکانت، ساخت توکن با یک الگو
(فقط‌خواندنی، همهٔ دسترسی‌های نقش یا انتخاب دستی مجوزها)، انقضا و IP مجاز اختیاری، دیدن یک‌بارهٔ
توکن، و ابطال توکن.

## محدودیت تلاش ورود

| سطح                  | سقف      | پنجره و قفل                                                        |
| -------------------- | -------- | ------------------------------------------------------------------ |
| هر حساب (hash ایمیل) | ۱۰ شکست  | ۱۵ دقیقه از اولین شکست؛ تا پایان پنجره حتی رمز درست هم 429 می‌گیرد |
| هر IP                | ۱۰۰ شکست | ۱۵ دقیقه؛ جلوی password spraying روی حساب‌های مختلف را می‌گیرد     |

- پاسخ قفل: **429 `login_locked`** با هدر `Retry-After` به ثانیه.
- ورود موفق شمارندهٔ حساب را صفر می‌کند.
- شمارنده‌ها روی Valkey هستند (`dirouter:login:*`)، پس بین replicaها مشترک‌اند. اگر Valkey در دسترس نباشد، شمارندهٔ حافظهٔ همان نود استفاده می‌شود: ورود از کار نمی‌افتد و محافظت هر نود جداگانه ادامه دارد.
- باز کردن دستی قفل:

  ```bash
  valkey-cli --scan --pattern 'dirouter:login:acct:*' | xargs valkey-cli del
  ```

## ویزارد setup

- در یک تراکنش با `pg_advisory_xact_lock`: شمارش کاربران، ساخت سازمان (slug از نام؛ برای نام فارسی، `org-xxxxxxxx`)، کاربر و عضویت OWNER، و ثبت `setup.completed` در audit log.
- دو درخواست هم‌زمان: دقیقاً یکی 201 و دیگری 409 می‌گیرد (تست integration).

## ثبت‌نام پرتال و تأیید ایمیل (کارت ۲۳.۴)

کد: `apps/control-api/src/portal` · تست‌ها: `portal.integration.test.ts` (با یک شنوندهٔ SMTP واقعی)

ثبت‌نام با رمز عبور در پرتال سلف‌سرویس (`POST /api/v1/portal/signup`) کاربر، فضای کاری پیش‌پرداخت و پروژهٔ پیش‌فرض آن را می‌سازد و کاربر را وارد می‌کند، اما نشانی ایمیل هنوز **تأیید نشده** است:

- `GET /auth/me` مقدار `emailVerified: false` برمی‌گرداند؛
- ساخت کلید API در هر سازمانی با **403 `email_not_verified`** رد می‌شود؛
- اعتبار هدیهٔ شروع (`portal.welcomeCreditUsd`) داده نمی‌شود.

ثبت‌نام یک لینک یک‌بارمصرف، `<PUBLIC_PORTAL_URL>/verify-email?token=…`، با SMTP (`SMTP_URL`، ببینید [هشدارها](../alerts.fa.md)) ایمیل می‌کند. توکن ۳۲ بایت تصادفی است و فقط SHA-256 آن، با انقضای ۲۴ ساعته، در `email_verifications` ذخیره می‌شود. پاسخ ثبت‌نام `emailVerified: false` و ارسال‌شدن یا نشدن ایمیل (`verificationEmailSent`) را می‌گوید.

| مسیر                               | توضیح                                                                                                                                                                                        |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /portal/verify-email`        | `{token}` بدون نیاز به نشست: نشانی را تأییدشده می‌کند و اعتبار هدیه را یک بار می‌دهد (کلید idempotency `welcome:<org>`). لینک با به‌روزرسانی شرطی گرفته می‌شود، پس دقیقاً یک بار کار می‌کند. |
| `POST /portal/verify-email/resend` | با Bearer: لینک تازه؛ لینک‌های استفاده‌نشدهٔ قبلی از کار می‌افتند. برای هر کاربر یکی در دقیقه و سه تا در ساعت (بیش از آن **429**)؛ اگر نشانی از قبل تأیید شده باشد **409**.                  |

لینک ناشناخته، استفاده‌شده یا منقضی با **400 `verification_link_invalid`** رد می‌شود و `detail` علت را می‌گوید. بدون `SMTP_URL` لینک هرگز نمی‌رسد، پس ثبت‌نام با رمز عبور رد می‌شود (403) و `GET /portal/config` مقدار `passwordSignup: false` را گزارش می‌کند؛ ثبت‌نام با OIDC همچنان کار می‌کند.

**OIDC**: ورود OIDC پرتال فقط ID tokenی را می‌پذیرد که `email_verified: true` دارد، پس حسابی که می‌سازد بی‌درنگ تأییدشده است (اعتبار و کلید فوراً، بدون ایمیل). اگر حسابی که با رمز عبور ساخته شده و لینکش را باز نکرده، بعداً با همان نشانی تأییدشده از OIDC وارد شود، همان موقع تأیید می‌شود.

هر راه دیگر ساخت حساب (ویزارد setup، دعوت، SSO، SCIM، seed) تأییدشده حساب می‌شود: مقدار پیش‌فرض ستون زمان ساخت است و migration حساب‌های موجود را تأییدشده می‌کند. پرتال تا تأیید نشانی، پیامی با دکمهٔ **ارسال دوبارهٔ لینک** نشان می‌دهد.
