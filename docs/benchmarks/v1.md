# v1 benchmark: gateway overhead, profile and optimization

Run date: 2026-11-23. Decision record: [ADR-0007](../../adr/0007-data-plane-stays-on-node.md).

## Method

- **Harness:** `scripts/bench/run-v1.py`. It builds the mock provider and the gateway, starts both
  as plain Node processes on the host with a generated snapshot (no proxy in front), and runs the
  same k6 script (`scripts/bench/k6-baseline.js`, `constant-arrival-rate`) against:
  - **direct**: the mock provider itself (the baseline);
  - **DiRouter**: the gateway, routing to the same mock provider;
  - **LiteLLM**: a LiteLLM proxy container pointed at the same mock provider (`--litellm-image`).
- **Payload:** `POST /v1/chat/completions`, model `mock/small`, one short user message.
  Stream runs ask for `stream_options.include_usage`. Every response is checked for content.
- **Per run:** 30 s at a fixed arrival rate. The script also records the CPU time the gateway
  process used during the run, giving CPU per request.
- **Profiling:** the gateway under `node --cpu-prof` at 600 RPS non-stream and stream, summarized
  by package and by function (self time). This is the same V8 sampling data that clinic.js and 0x
  render as flame graphs.

Reproduce:

```bash
python3 scripts/bench/run-v1.py --output .bench/v1
```

```bash
python3 scripts/bench/run-v1.py --output .bench/v1-low --rates nonstream=250,nonstream=500
```

## Hardware

|                           |                                                                                                           |
| ------------------------- | --------------------------------------------------------------------------------------------------------- |
| Host                      | MacBook Pro, Apple M1 Pro, 8 cores (6 performance, 2 efficiency), 16 GB                                   |
| Gateway and mock provider | Native Node.js v22.17.0 (arm64) on the host                                                               |
| Load generator            | `grafana/k6` in Docker Desktop (VM with 4 CPUs, 3.8 GB), reaching the host through `host.docker.internal` |

> This is a shared development machine; the k6 VM adds roughly 3 ms of network path to every
> request, which is why the direct p50 is about 3.4 ms. Overhead is read as DiRouter minus direct
> at the same rate. For publishable capacity figures, rerun on dedicated hardware with the load
> generator on a separate machine.

## Results

### Overhead by load (non-stream, one gateway process)

| Rate    | Direct p50 / p95 / p99 | DiRouter p50 / p95 / p99 | Overhead p50 / p95 / p99  | Failed |
| ------- | ---------------------- | ------------------------ | ------------------------- | ------ |
| 250/s   | 3.32 / 4.63 / 6.55 ms  | 4.46 / 6.94 / 9.35 ms    | +1.1 / +2.3 / **+2.8 ms** | 0      |
| 500/s   | 3.37 / 4.88 / 7.35 ms  | 4.01 / 6.92 / 14.54 ms   | +0.6 / +2.0 / +7.2 ms     | 0      |
| 1 000/s | 3.46 / 5.12 / 9.15 ms  | 3.63 / 8.17 / 40.47 ms   | +0.2 / +3.1 / +31.3 ms    | 0      |

### Stream (500/s)

|          | p50      | p95      | p99      | Failed |
| -------- | -------- | -------- | -------- | ------ |
| Direct   | 10.75 ms | 14.02 ms | 16.90 ms | 0      |
| DiRouter | 9.46 ms  | 12.20 ms | 16.13 ms | 0      |

Streams are paced by the mock provider; DiRouter adds no measurable latency at this rate (the
difference is within run-to-run noise).

### CPU per request

| Mode       | Rate    | Gateway CPU per request |
| ---------- | ------- | ----------------------- |
| Non-stream | 1 000/s | 0.54 ms                 |
| Stream     | 500/s   | 0.97 ms                 |

At low rates the figure is higher (1.5 ms at 250/s) because the process's fixed background work
is divided by fewer requests.

## Profile and optimization

Gateway self time at 600 RPS, before the change (share of busy CPU):

| Share | Where                                                                    |
| ----- | ------------------------------------------------------------------------ |
| 28.9% | Node core (sockets, streams, timers)                                     |
| 14.7% | `packages/routing`, almost all of it `RouterStats.recordRequest` (13.5%) |
| 11.3% | undici (upstream HTTP)                                                   |
| 9.8%  | gateway request handling                                                 |
| 7.5%  | garbage collection                                                       |

`recordRequest` kept a timestamp per request and filtered the whole list on every request: at
_n_ requests per minute each call cost O(_n_), so the cost grew with traffic. It now counts
requests in sixty one-second buckets with a running total (O(1) amortized to record and to read).

Effect, measured A/B on the same machine (1 000/s non-stream plus 500/s stream, 30 s each, 45 000
requests): gateway CPU time **35.1 s → 30.8 s (−12.4%)**, matching the profile. Latency at these
rates did not change measurably, because a single gateway process was not CPU-bound there.

The remaining profile has no other single hotspot in DiRouter code: the largest items are socket
I/O, the HTTP client and garbage collection.

## Reading the results

- The ADR-0001 target, **hot-path p99 overhead below 5 ms**, is met at 250 requests per second per
  gateway process on this hardware, and missed at 500 and above.
- The tail grows with load on one process (event-loop queueing and GC), while p50 and p95 overhead
  stay at a few milliseconds. That is the signature of a single-threaded process near saturation,
  not of a fixed per-request cost, so it is addressed by running more replicas, each below the
  load where its tail stays within target.
