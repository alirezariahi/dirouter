# benchmark نسخهٔ v1: overhead گیت‌وی، profile و بهینه‌سازی

تاریخ اجرا: ۲۰۲۶-۱۱-۲۳. سند تصمیم: [ADR-0007](../../adr/0007-data-plane-stays-on-node.fa.md).

## روش

- **Harness:** `scripts/bench/run-v1.py`. این اسکریپت mock provider و گیت‌وی را می‌سازد، هر دو را به‌صورت پروسهٔ Node معمولی روی میزبان با یک snapshot ساخته‌شده اجرا می‌کند (بدون proxy جلوی آن‌ها)، و یک اسکریپت k6 یکسان (`scripts/bench/k6-baseline.js` با `constant-arrival-rate`) را روی این هدف‌ها اجرا می‌کند:
  - **مستقیم**: خود mock provider (خط مبنا)؛
  - **DiRouter**: گیت‌وی که به همان mock provider مسیریابی می‌کند؛
  - **LiteLLM**: یک کانتینر LiteLLM که به همان mock provider وصل است (`--litellm-image`).
- **بار:** `POST /v1/chat/completions` با مدل `mock/small` و یک پیام کوتاه کاربر. اجراهای stream مقدار `stream_options.include_usage` را می‌خواهند. محتوای هر پاسخ بررسی می‌شود.
- **هر اجرا:** ۳۰ ثانیه با نرخ ورود ثابت. اسکریپت زمان CPU پروسهٔ گیت‌وی در طول اجرا را هم ثبت می‌کند، که از آن CPU هر درخواست به دست می‌آید.
- **Profiling:** گیت‌وی با `node --cpu-prof` در ۶۰۰ درخواست در ثانیه (غیر-stream و stream)، خلاصه‌شده بر اساس بسته و تابع (self time). این همان دادهٔ نمونه‌برداری V8 است که clinic.js و 0x به‌صورت flame graph نشان می‌دهند.

اجرای دوباره:

```bash
python3 scripts/bench/run-v1.py --output .bench/v1
```

```bash
python3 scripts/bench/run-v1.py --output .bench/v1-low --rates nonstream=250,nonstream=500
```

## نتایج

### overhead بر حسب بار (غیر-stream، یک پروسهٔ گیت‌وی)

| نرخ           | مستقیم p50 / p95 / p99 | DiRouter p50 / p95 / p99 | overhead p50 / p95 / p99   | خطا |
| ------------- | ---------------------- | ------------------------ | -------------------------- | --- |
| ۲۵۰ در ثانیه  | 3.32 / 4.63 / 6.55 ms  | 4.46 / 6.94 / 9.35 ms    | ‎+1.1 / +2.3 / **+2.8 ms** | ۰   |
| ۵۰۰ در ثانیه  | 3.37 / 4.88 / 7.35 ms  | 4.01 / 6.92 / 14.54 ms   | ‎+0.6 / +2.0 / +7.2 ms     | ۰   |
| ۱۰۰۰ در ثانیه | 3.46 / 5.12 / 9.15 ms  | 3.63 / 8.17 / 40.47 ms   | ‎+0.2 / +3.1 / +31.3 ms    | ۰   |

### stream (۵۰۰ در ثانیه)

|          | p50      | p95      | p99      | خطا |
| -------- | -------- | -------- | -------- | --- |
| مستقیم   | 10.75 ms | 14.02 ms | 16.90 ms | ۰   |
| DiRouter | 9.46 ms  | 12.20 ms | 16.13 ms | ۰   |

سرعت streamها را mock provider تعیین می‌کند. DiRouter در این نرخ تأخیر قابل‌اندازه‌گیری اضافه نمی‌کند (تفاوت در حد نوسان بین اجراهاست).

### CPU هر درخواست

| حالت       | نرخ           | CPU گیت‌وی برای هر درخواست |
| ---------- | ------------- | -------------------------- |
| غیر-stream | ۱۰۰۰ در ثانیه | 0.54 ms                    |
| stream     | ۵۰۰ در ثانیه  | 0.97 ms                    |

در نرخ‌های پایین این عدد بالاتر است (1.5 ms در ۲۵۰ در ثانیه)، چون کار ثابت پس‌زمینهٔ پروسه بر درخواست‌های کمتری تقسیم می‌شود.

### LiteLLM

**هنوز اجرا نشده.** harness از آن پشتیبانی می‌کند (`--litellm-image ghcr.io/berriai/litellm:<tag>`)، اما فقط از ایمیجی استفاده می‌کند که از قبل روی ماشین هست، و ایمیج LiteLLM روی میزبان benchmark دانلود نشده است. مقایسه هر وقت اجرا شد به همین بخش اضافه می‌شود.

## profile و بهینه‌سازی

self time گیت‌وی در ۶۰۰ درخواست در ثانیه، پیش از تغییر (سهم از CPU مشغول):

| سهم   | کجا                                                                   |
| ----- | --------------------------------------------------------------------- |
| ۲۸.۹٪ | هستهٔ Node (سوکت‌ها، streamها، تایمرها)                               |
| ۱۴.۷٪ | `packages/routing`، تقریباً تمامش `RouterStats.recordRequest` (۱۳.۵٪) |
| ۱۱.۳٪ | undici (HTTP به upstream)                                             |
| ۹.۸٪  | پردازش درخواست در گیت‌وی                                              |
| ۷.۵٪  | garbage collection                                                    |

`recordRequest` برای هر درخواست یک timestamp نگه می‌داشت و در هر درخواست کل فهرست را فیلتر می‌کرد. با _n_ درخواست در دقیقه هر فراخوانی O(_n_) هزینه داشت و هزینه با ترافیک رشد می‌کرد. حالا درخواست‌ها در شصت سطل یک‌ثانیه‌ای با یک جمع جاری شمرده می‌شوند (ثبت و خواندن، هر دو به‌طور سرشکن O(1)).

اثر، با سنجش A/B روی همان ماشین (۱۰۰۰ غیر-stream به‌علاوهٔ ۵۰۰ stream در ثانیه، هر کدام ۳۰ ثانیه، ۴۵٬۰۰۰ درخواست): زمان CPU گیت‌وی از **۳۵.۱ ثانیه به ۳۰.۸ ثانیه (۱۲.۴٪ کمتر)**، که با profile می‌خواند. تأخیر در این نرخ‌ها تغییر محسوسی نکرد، چون یک پروسهٔ گیت‌وی آنجا محدود به CPU نبود.

در profile باقی‌مانده گلوگاه دیگری در کد DiRouter نیست: بزرگ‌ترین بخش‌ها I/O سوکت، کلاینت HTTP و garbage collection هستند.

## خوانش نتایج

- هدف ADR-0001، یعنی **overhead مسیر داغ در p99 زیر ۵ میلی‌ثانیه**، روی این سخت‌افزار در ۲۵۰ درخواست در ثانیه برای هر پروسهٔ گیت‌وی برقرار است و در ۵۰۰ و بالاتر نه.
- tail با بار روی یک پروسه رشد می‌کند (صف event loop و GC)، در حالی که overhead در p50 و p95 چند میلی‌ثانیه می‌ماند. این نشانهٔ یک پروسهٔ تک‌thread نزدیک به اشباع است، نه هزینهٔ ثابت هر درخواست. راه حلش replica بیشتر است، هر کدام زیر باری که tail آن در هدف بماند.
