# بدنهٔ درخواست، نمایش payload و replay

> کد: `apps/gateway/src/body-capture.ts`، `packages/contracts/src/request-body.ts`، تابع `redactForStorage` در `packages/contracts/src/guardrail-engine.ts`، `apps/worker/src/request-bodies.ts` و `apps/control-api/src/bodies` (کارت ۲۴.۱). داشبورد: **لاگ‌ها** (payload در جزئیات درخواست و سطح ثبت زیر جدول) و **Playground** (اجرای دوباره).

لاگ درخواست ثبت می‌کند چه بر سر درخواست آمد (مدل، provider، وضعیت، توکن و هزینه). برای خطایابی یک درخواست بدون حدس زدن محتوای آن، گیت‌وی می‌تواند بدنهٔ درخواست و پاسخ را هم نگه دارد. این قابلیت **به‌طور پیش‌فرض خاموش** است.

## سطح ثبت

| سطح        | چه چیزی ذخیره می‌شود                                                                                                                                                         |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `none`     | هیچ (پیش‌فرض).                                                                                                                                                               |
| `metadata` | فقط شکل درخواست: مدل درخواستی، `stream`، نام پارامترهایی که کلاینت فرستاده (نه مقدارشان)، تعداد پیام هر نقش، نام ابزارها، حجم درخواست و پاسخ به بایت و دلیل پایان. بدون متن. |
| `full`     | همهٔ موارد `metadata` به‌علاوهٔ JSON درخواست همان‌طور که کلاینت فرستاده و JSON پاسخ، هر دو ماسک‌شده و بریده در سقف حجم، و یک پیش‌نویس replay برای playground.                |

سطح برای **سازمان**، **پروژه** یا **کلید مجازی** تعیین می‌شود و دقیق‌ترین آن‌ها برنده است: سطح خود کلید، وگرنه سطح پروژه، وگرنه سطح سازمان، وگرنه پیش‌فرض نمونه. پیش‌فرض نمونه `settings.bodyCapture.defaultLevel` در تنظیمات گیت‌وی است (فقط OWNER، صفحهٔ **Config**)؛ اگر نباشد، تنظیم قدیمی `settings.logBodies: true` یعنی `full` و در غیر این صورت `none`.

سطح‌ها در داشبورد (**لاگ‌ها**، بخش «ثبت بدنهٔ درخواست») یا با API زیر تغییر می‌کنند. هر تغییر در audit log (`body_capture.updated`) ثبت و در snapshot پیکربندی (`bodyCapture`) منتشر می‌شود و گیت‌وی پس از بارگذاری همان snapshot آن را اعمال می‌کند.

## ماسک کردن و سقف حجم

پیش از آن‌که بدنه از گیت‌وی خارج شود:

۱. هر رشته در درخواست و پاسخ از **سیاست‌های guardrail با action برابر `redact`** که روی کلید اعمال می‌شوند عبور می‌کند (سیاست‌های سازمان، پروژه یا کلید با stage مطابق). تطابق‌ها با `[REDACTED]` ماسک می‌شوند، درست مثل ترافیک زنده. سیاست‌های `block` و `flag` چیزی را در ذخیره تغییر نمی‌دهند.
۲. کلیدها و اطلاعات محرمانه (الگوهای نوع `secret`: کلید providerها، کلید DiRouter، JWT و کلید خصوصی) **همیشه** ماسک می‌شوند، صرف‌نظر از سیاست‌ها.
۳. هر بخش (درخواست و پاسخ) در `settings.bodyCapture.maxBytes` (پیش‌فرض ۶۵٬۵۳۶ بایت، از ۱ کیلوبایت تا ۱ مگابایت) روی مرز کاراکتر بریده و «بریده‌شده» علامت می‌خورد. درخواست بریده‌شده JSON معتبر نیست و به‌صورت متن نمایش داده می‌شود.

تعداد موارد ماسک‌شده کنار بدنه ذخیره می‌شود. ماسک کردن روی ساختار parse‌شده و پیش از بریدن انجام می‌شود، پس بریدن هیچ‌وقت نیمی از یک تطابق را باقی نمی‌گذارد.

پاسخ stream به‌صورت یک پاسخ JSON کامل (در قالب API کلاینت) ذخیره و `streamed` علامت می‌خورد. این پاسخ از آنچه provider فرستاده و پیش از guardrailهای stream بازسازی می‌شود و سیاست‌های `redact` در گام ۱ دوباره روی آن اعمال می‌شوند. اگر stream پیش از پایان قطع شود فقط درخواست ذخیره می‌شود. پاسخ‌های خطا (4xx و 5xx خود گیت‌وی) همان‌طور که کلاینت دریافت کرده ذخیره می‌شوند.

فقط endpointهای گفت‌وگو (`/v1/chat/completions`، `/v1/messages`، `/v1/responses` و `generateContent` جمینای) ثبت می‌شوند؛ embeddings، تصویر، گفتار و رونویسی نه.

## مسیر ذخیره

```
gateway ──(پایان پاسخ)──▶ BullMQ "request-bodies" ──▶ worker ──▶ request_bodies (پارتیشن روزانه)
```

- بدنه **هرگز** همراه usage event نمی‌رود. صف خودش را دارد (`request-bodies`)، پس پرامپت بزرگ حجم صف `usage` را بالا نمی‌برد و صورت‌حساب منتظر بدنه نمی‌ماند.
- ارسال best effort است: اگر Valkey در دسترس نباشد یا بیش از ۲۰۰ بدنه منتظر صف باشند، بدنه دور ریخته می‌شود. خود درخواست و usage event آن هیچ اثری نمی‌پذیرند.
- worker هر بدنه را یک بار می‌نویسد (`ON CONFLICT DO NOTHING` روی `(request_id, created_at)`)؛ `created_at` همان لحظهٔ ردیف `request_log` است.
- جدول `request_bodies` در schema `partitions` به‌صورت **روزانه** پارتیشن می‌شود. worker هر ساعت پارتیشن امروز و سه روز بعد را می‌سازد (`body-partitions`) و هر روز ساعت 03:27 UTC روزهای کامل قدیمی‌تر از `REQUEST_BODY_RETENTION_DAYS` (پیش‌فرض ۷) را حذف می‌کند (`body-retention`). این retention مستقل از `REQUEST_LOG_RETENTION_MONTHS` است: بدنه‌ها معمولاً خیلی زودتر از ردیف لاگ حذف می‌شوند. نگاه کنید به [پایگاه داده](../database.fa.md).

## دیدن payload

برای همهٔ موارد این بخش مجوز **`logs:bodies`** لازم است. این مجوز از نوع `:read` نیست: OWNER و ADMIN آن را دارند و MEMBER و VIEWER ندارند مگر نقش سفارشی آن را اضافه کند. بدون آن، Log Explorer بخش payload را نشان نمی‌دهد و اصلاً بدنه را درخواست نمی‌کند؛ `usage:read` به‌تنهایی بدنه را آشکار نمی‌کند.

| مسیر                             | مجوز          | توضیح                                                                                                                       |
| -------------------------------- | ------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `GET /orgs/:orgId/logs/:id/body` | `logs:bodies` | بدنهٔ ذخیره‌شدهٔ یک درخواست؛ اگر ثبت نشده یا منقضی شده باشد 404                                                             |
| `GET /orgs/:orgId/body-capture`  | `logs:bodies` | سطح‌های تعیین‌شدهٔ سازمان، پیش‌فرض نمونه و سقف حجم                                                                          |
| `PUT /orgs/:orgId/body-capture`  | `logs:bodies` | `{scope: organization \| project \| key, scopeId, level: none \| metadata \| full \| inherit}`؛ `inherit` سطح را حذف می‌کند |

بدنه فقط درون سازمان خودش برگردانده می‌شود؛ پروژه یا کلید سازمان دیگر «پیدا نشد» است.

## اجرای دوباره (replay)

بدنهٔ سطح `full` یک پیش‌نویس replay دارد: متن system، همهٔ پیام‌های قبلی کاربر و دستیار به‌صورت متن ساده، آخرین پیام کاربر به‌عنوان prompt، و `max_tokens` و `temperature`. دکمهٔ **اجرای دوباره در playground** صفحهٔ playground را با همین گفت‌وگو باز می‌کند؛ هر مدلی را می‌توان انتخاب کرد و درخواست مثل هر فراخوانی playground با کلید خود کاربر از گیت‌وی عبور می‌کند. تصویر، فراخوانی ابزار و نتیجهٔ ابزار قابل اجرای دوباره نیستند و کنار گذاشته می‌شوند و playground این را اعلام می‌کند. پیش‌نویس مثل بدنه ماسک می‌شود، پس مقدار ماسک‌شده ماسک‌شده اجرا می‌شود.

پیش‌نویس از طریق `sessionStorage` مرورگر تحویل داده و یک بار خوانده می‌شود، پس prompt هرگز در URL نمی‌آید.
