# کش و صرفه‌جویی توکن

> کد: `apps/gateway/src/{cache,compress}.ts`، `apps/control-api/src/semantic-cache` (کارت‌های ۱۳.۱ تا ۱۳.۳). همهٔ این قابلیت‌ها **به‌صورت پیش‌فرض خاموش‌اند** و از تنظیمات گیت‌وی روشن می‌شوند (`PUT /orgs/:orgId/config/settings`، بخش «تنظیمات سراسری گیت‌وی» در [routing.fa.md](routing.fa.md)).

## ۱. Exact cache (۱۳.۱)

وقتی همان پروژه درخواستی بایت‌به‌بایت یکسان برای همان مدل بفرستد، پاسخ قبلی دوباره استفاده می‌شود.

```json
{
  "cache": {
    "exact": { "enabled": true, "ttlSeconds": 300, "maxOutputTokens": 4096, "maxTemperature": 0.2 }
  }
}
```

- **کلید**: SHA-256 از سازمان، **پروژه**، مدل resolveشده، system prompt، پیام‌ها، ابزارها، tool choice، قالب پاسخ، `max_tokens`، `temperature`، `top_p`، `top_k`، `stop`، `seed` و `user`. هدرها جزو کلید نیستند.
- **ایزوله‌سازی**: شناسهٔ پروژه جزو کلید است؛ دو پروژهٔ یک سازمان حتی با prompt یکسان پاسخ هم را نمی‌خوانند.
- **شرط کش شدن**: فقط درخواست‌هایی با `temperature` حداکثر `maxTemperature` (یا بدون آن) و `max_tokens` حداکثر `maxOutputTokens`.
- **ذخیره‌سازی**: یک LRU در هر replica (۱۰۰۰ ورودی) به‌علاوهٔ Valkey در صورت وجود؛ با قطعی Valkey فقط LRU محلی کار می‌کند.
- **Stream**: `stream` جزو کلید نیست. hit برای کلاینت stream به‌صورت stream واقعی و با همان قالب کلاینت پخش می‌شود (chunkهای OpenAI، رویدادهای Anthropic، رویدادهای Responses یا chunkهای Gemini)، نه بدنهٔ JSON. streamی که سالم تمام شود هم کش را پر می‌کند، پس ابزارهای agent که همیشه stream می‌کنند hit می‌گیرند. streamی که guardrail متنش را بازنویسی کرده کش نمی‌شود.
- **هدرها**: hit با `x-dirouter-cache: exact` (یا `semantic`) برمی‌گردد. کلاینت می‌تواند با `x-dirouter-cache: bypass` یا `cache-control: no-cache` کش را برای یک درخواست دور بزند؛ چنین درخواستی ذخیره هم نمی‌شود.
- **حسابداری**: hit با `cache_hit`، `cache_kind` و توکن‌های پاسخ کش‌شده و با هزینهٔ صفر لاگ می‌شود.

## ۲. Semantic cache (۱۳.۲)

وقتی سؤال جدید هم‌معنی یک سؤال قبلی باشد، پاسخ قبلی استفاده می‌شود. بردارها در Postgres (`pgvector`) و پشت control-api هستند؛ گیت‌وی با timeout کوتاه می‌پرسد و هر خطا را miss حساب می‌کند (fail-open).

```json
{
  "cache": {
    "semantic": {
      "enabled": false,
      "threshold": 0.95,
      "ttlSeconds": 3600,
      "timeoutMs": 150,
      "embeddingModel": "text-embedding-3-small",
      "projects": {
        "prj_support": { "enabled": true, "threshold": 0.92 },
        "prj_code": { "enabled": false }
      }
    }
  }
}
```

- **پیش‌نیازها**: دیتابیس باید با imageی اجرا شود که افزونهٔ pgvector را دارد. image پیش‌فرض `postgres:17-alpine` آن را ندارد: `deploy/docker/postgres.Dockerfile` را بسازید و `POSTGRES_IMAGE` را تنظیم کنید (همان image پایه است و volume دادهٔ موجود دوباره استفاده می‌شود). جدول کش به‌محض در دسترس بودن افزونه خودکار ساخته می‌شود. `SEMANTIC_CACHE_EMBEDDING_URL` هم باید تنظیم شده باشد.
- **به ازای هر پروژه**: `projects.<projectId>` مقدارهای `enabled`، `threshold` و `embeddingModel` را برای یک پروژه بازنویسی می‌کند؛ بقیه از بلوک سراسری می‌آید. مثال بالا کش را فقط برای یک پروژه روشن می‌کند.
- **مدل امبدینگ**: control-api آدرس `SEMANTIC_CACHE_EMBEDDING_URL` را (هر endpoint سازگار با OpenAI، از جمله `/v1/embeddings` خود DiRouter) با `SEMANTIC_CACHE_EMBEDDING_MODEL` یا مقدار بازنویسی‌شده صدا می‌زند. ستون بردار ۱۵۳۶ بعدی است؛ مدلی با اندازهٔ دیگر رد می‌شود و درخواست miss است.
- **ایزوله‌سازی**: ورودی‌ها به سازمان، پروژه، مدل درخواستی و مدل امبدینگ محدودند. بردارهای دو مدل امبدینگ هرگز با هم مقایسه نمی‌شوند.
- **محدودیت‌های ایمنی**: فقط یک نوبت تک‌پیامِ متنی کاربر، بدون ابزار و بدون قالب پاسخ JSON واجد شرایط است. در گفت‌وگوی چندنوبتی یا ابزاری، همان پیام آخر («بله»، «ادامه بده») هر بار معنای دیگری دارد؛ این درخواست‌ها همیشه به upstream می‌روند.
- **آمار**: `GET /orgs/:orgId/stats/cache?from=&to=&projectId=` تعداد درخواست، hit و نرخ hit هر نوع کش، توکن و هزینهٔ providerی که صرفه‌جویی شده (با قیمت فعلی مدل) و توکن‌های حذف‌شده با فشرده‌سازی را می‌دهد. صفحهٔ «هزینه» همین اعداد را نشان می‌دهد.
- مدیریت: `GET /orgs/:orgId/cache/semantic` (تعداد ورودی‌ها) و `DELETE` برای پاک کردن ورودی‌های سازمان.

## ۳. فشرده‌سازی کانتکست (۱۳.۳)

گفت‌وگوهای طولانی agent را پیش از مسیریابی کوچک می‌کند. فقط روی پیام‌های قدیمی‌تر از `keepRecentMessages` پیام آخر اعمال می‌شود.

```json
{
  "compression": {
    "enabled": true,
    "dedupe": true,
    "maxToolResultChars": 2000,
    "keepRecentMessages": 4,
    "dropOldReasoning": true
  }
}
```

| مرحله               | چه اتفاقی می‌افتد                                                                                                                   |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| پاک‌سازی خروجی      | کدهای escape ترمینال، فاصلهٔ انتهای خط، خط‌های خالی پیاپی و خط‌های تکراری (بیش از ۳ بار) جمع می‌شوند                                |
| پاک‌سازی `git diff` | خط‌های `index abc..def`، mode فایل و similarity حذف می‌شوند؛ hunkها دست نمی‌خورند                                                   |
| حذف تکرار           | نتیجهٔ ابزاری که عیناً تکرار یک نتیجهٔ قبلی است (۲۰۰ نویسه به بالا) با `[same output as the earlier tool call <id>]` جایگزین می‌شود |
| سر و ته             | نتیجهٔ بلندتر از `maxToolResultChars`، ۶۰٪ اول و ۴۰٪ آخر بودجه را نگه می‌دارد و طول بخش حذف‌شده را می‌نویسد                         |
| reasoning قدیمی     | بلوک‌های reasoning از پیام‌های قدیمی‌ای که محتوای دیگری هم دارند حذف می‌شوند                                                        |

**تضمین ساختار.** فشرده‌ساز هرگز پیامی را حذف نمی‌کند و هیچ `tool_call` یا `tool_result`ی را حذف، جابه‌جا یا با شناسهٔ دیگر نمی‌کند. providerها گفت‌وگویی را که callها و resultهایش جفت نباشند رد می‌کنند؛ برای همین بعد از فشرده‌سازی، ساختار tool-call با نسخهٔ اصلی مقایسه می‌شود و با هر تفاوتی، درخواست اصلی بدون تغییر ارسال می‌شود. نتیجه‌های دارای تصویر و پیام‌های اخیر هرگز تغییر نمی‌کنند.

نویسه‌های صرفه‌جویی‌شده به‌صورت `savedInputTokens` (نویسه تقسیم بر ۴) در رویداد مصرف و `request_log.saved_input_tokens` ثبت می‌شوند.

**مجموعهٔ ارزیابی.** `apps/gateway/test-fixtures/compression/*.json` گفت‌وگوهایی به قالب canonical است؛ `compress.test.ts` فشرده‌ساز را روی هر کدام اجرا می‌کند، تضمین‌های بالا را می‌سنجد و میزان صرفه‌جویی را چاپ می‌کند. فایل همراه `synthetic-claude-code.json` دست‌نویس و به شکل خروجی Claude Code است (۸۴٪ صرفه‌جویی با تنظیم‌های تست)؛ نشست واقعیِ ضبط‌شده نیست. برای ارزیابی روی ترافیک خودتان، رونوشت‌های واقعی و پاک‌سازی‌شده را در همان پوشه بگذارید.
