# سیاست‌های مسیریابی

> کد: `packages/routing` (`rules-expr.ts` و `rules.ts`)، مرحلهٔ گیت‌وی در
> `apps/gateway/src/routing-policy.ts`، API در `apps/control-api/src/routing-policies` و صفحهٔ
> **سیاست‌های مسیریابی** در داشبورد (اسپرینت ۵).

سیاست‌های مسیریابی روی هر درخواست **پیش از** انتخاب مدل اجرا می‌شوند: بعد از احراز هویت، گاردریل و
فشرده‌سازی و قبل از مسیریابی `auto*` و resolver [مسیریابی](routing.fa.md). همهٔ مراحل بعدی مقصد سیاست
را طوری می‌بینند که انگار مشتری همان را خواسته؛ پاسخ همچنان نامی را دارد که مشتری فرستاده است.

## ۱. قانون‌های شرطی (کارت ۳۲.۲)

هر قانون یک شرط و یک اقدام دارد. قانون‌های یک سازمان به **ترتیب اولویت** (عدد کمتر اول) اجرا
می‌شوند. اولین `route` یا `reject` منطبق تصمیم می‌گیرد؛ `tag` منطبق برچسب اضافه می‌کند و ارزیابی
ادامه می‌یابد.

| اقدام    | اثر                                                                       |
| -------- | ------------------------------------------------------------------------- |
| `route`  | ارسال به مدل، alias، combo یا نام `auto*` دیگری از سازمان                 |
| `reject` | رد درخواست با پیام و کد وضعیت قانون (۴۰۳، ۴۰۰ یا ۴۲۹)                     |
| `tag`    | ثبت حداکثر ۱۰ برچسب `key=value` همراه درخواست (رویداد مصرف و لاگ درخواست) |

قانون برای کل سازمان است یا فقط برای کلیدهای یک **تیم** (سیاست جدای هر تیم) یا یک پروژه. قانون
هیچ‌وقت دسترسی کلید را بیشتر نمی‌کند: `allowedModels` کلید پیش از اجرای قانون‌ها روی نامی که مشتری
فرستاده بررسی می‌شود.

### زبان عبارت

زیرمجموعهٔ امنی از CEL. شرط هنگام **ذخیره** تجزیه و نوع‌سنجی می‌شود (شرط نامعتبر با ۴۰۰ و محل
مشکل رد می‌شود) و گیت‌وی هنگام بارگذاری snapshot آن را به closure تبدیل می‌کند. حلقه، عبارت باقاعده
و تابع تعریف‌شده توسط کاربر وجود ندارد، پس هر عبارت در زمانی متناسب با طولش تمام می‌شود.

| متغیر                                                       | نوع  | معنا                                                                 |
| ----------------------------------------------------------- | ---- | -------------------------------------------------------------------- |
| `request.model`                                             | رشته | نامی که مشتری فرستاده                                                |
| `request.api`                                               | رشته | `openai.chat`، `anthropic.messages` و …                              |
| `request.stream`، `request.has_tools`، `request.has_images` | بولی |                                                                      |
| `request.headers['x-tier']`                                 | رشته | هدر درخواست (حروف کوچک)؛ هدرهای اعتبار مثل `authorization` پنهان‌اند |
| `request.metadata.feature`                                  | رشته | فیلد `metadata` درخواست                                              |
| `request.estimated_tokens`، `request.max_output_tokens`     | عدد  | تخمین ورودی و سقف خروجی                                              |
| `request.user`                                              | رشته | شناسهٔ کاربر نهایی                                                   |
| `key.id`، `key.team`، `key.project`، `key.organization`     | رشته | کلید فراخوان (`key.team` بدون تیم خالی است)                          |
| `budget.key`، `budget.project`، `budget.team`، `budget.max` | عدد  | درصد مصرف‌شدهٔ بودجهٔ دورهٔ جاری (بدون بودجه ۰)                      |

عملگرها: `|| && ! == != < <= > >= in + - * / %`؛ تابع‌های `size()`، `has()`، `int()`، `double()`،
`string()`؛ متدهای رشته `startsWith`، `endsWith`، `contains`، `lowerAscii`.

```text
budget.team > 80                                     → ارسال به مدل ارزان
request.headers['x-tier'] == 'gold'                  → ارسال به بهترین مدل
request.metadata.feature in ['search', 'autocomplete'] → برچسب feature=search
request.estimated_tokens > 100000 && key.team == ''  → رد (۴۰۰)
```

### مصرف بودجه

وقتی قانونی `budget.*` را می‌خواند، گیت‌وی شمارنده‌های کلید، پروژه و تیم را از Valkey می‌خواند (یک
رفت‌وبرگشت، با کش یک‌ثانیه‌ای برای هر بودجه). بدون Valkey همهٔ سهم‌ها ۰ خوانده می‌شوند.

### هزینه روی مسیر داغ

معیار کمتر از ۰٫۲ میلی‌ثانیه به ازای هر درخواست است؛ بستهٔ routing مجموعهٔ واقع‌گرایانهٔ ۲۰ قانون را
در حد چند میکروثانیه اندازه می‌گیرد (`rules.test.ts`). سازمان بدون قانون فقط یک جست‌وجوی map می‌پردازد.

### API

| متد و مسیر                                                    | مجوز           |
| ------------------------------------------------------------- | -------------- |
| `GET /orgs/:orgId/routing/rules`                              | `models:read`  |
| `POST /orgs/:orgId/routing/rules` و `PATCH`/`DELETE …/:id`    | `models:write` |
| `POST /orgs/:orgId/routing/rules/validate` با `{ condition }` | `models:read`  |
| `GET /orgs/:orgId/routing/rules/traffic?from&to`              | `usage:read`   |

گزارش ترافیک برای هر قانون تعداد درخواست‌های منطبق و تصمیم‌گرفته و سهم آن از درخواست‌های سازمان در
بازه (پیش‌فرض ۲۴ ساعت گذشته) را از ستون `policy` لاگ درخواست می‌شمارد. شبیه‌ساز مسیریابی
(`POST /orgs/:orgId/routes/simulate`) فیلدهای `headers`، `metadata` و `budget: { key, project, team }`
را می‌پذیرد و قانون‌های منطبق و مقصد نهایی را برمی‌گرداند.

هر درخواست کار قانون‌ها را در `policy.rules` رویداد مصرف (`matched`، `decidedBy`، `target`، `tags`)
ثبت می‌کند و پاسخ هدر `x-dirouter-rule` را با قانون تصمیم‌گیرنده دارد.

## ۲. canary و تقسیم درصدی ترافیک (کارت ۳۲.۳)

هر تقسیم، درخواست‌های یک نام (`match`، چیزی که مشتری یا یک قانون می‌خواهد) را به اندازهٔ
`canaryPercent` از ترافیک (۰ تا ۱۰۰، دو رقم اعشار) به مقصد `canary` و بقیه را به `stable` می‌فرستد.
درست بعد از قانون‌ها اجرا می‌شود، پس مقصد یک قانون هم می‌تواند تقسیم شود.

- **چسبندگی.** `key` (پیش‌فرض) هر کلید را روی شاخه‌اش نگه می‌دارد، `session` هر نشست را (هدر
  session affinity، پیش‌فرض `x-dirouter-session`، و در نبودش کلید) و `request` برای هر درخواست
  قرعه می‌کشد. شاخه از hash شناسهٔ تقسیم و شناسهٔ هویت در ۱۰٬۰۰۰ سطل به دست می‌آید: بالا بردن درصد
  فقط هویت‌های پایدار را به canary می‌برد. در ۱۰٬۰۰۰ هویت، سهم واقعی در ±۱٪ مقدار تنظیم‌شده است
  (`split.test.ts`، `traffic-split.test.ts` و سناریوی end-to-end).
- **نسخه‌ها.** هر تغییر یک نسخهٔ تازه با دلیلش است (`created`، `updated`، `rollback`،
  `auto_rollback`، `restore`). `POST …/rollback` بدون بدنه همه‌چیز را فوراً به پایدار برمی‌گرداند
  (وضعیت `rolled_back`)؛ با `{ toVersion }` تنظیمات آن نسخه نسخهٔ تازه می‌شود. تغییر canary یا سهم
  آن، یا `PATCH { state: 'active' }`، تقسیم برگشت‌خورده را از سر می‌گیرد.
- **بازگشت خودکار.** با `autoRollback` (`errorRate` پیش‌فرض ۰٫۲، `minRequests` پیش‌فرض ۲۰،
  `windowSeconds` پیش‌فرض ۶۰) گیت‌وی شکست‌های canary (هر پاسخ 5xx، از جمله نبود provider در دسترس)
  را در پنجرهٔ غلتان می‌پاید. با عبور نرخ از آستانه، همان replica فوراً canary را کنار می‌گذارد،
  پرچم `dirouter:split:rolledback:<id>:<version>` را در Valkey می‌گذارد (replicaهای دیگر هر دو ثانیه
  این پرچم‌ها را می‌خوانند) و رویدادی در `dirouter:splits:rollbacks` می‌گذارد که control-api در چند
  ثانیه به نسخهٔ تازهٔ `rolled_back` تبدیلش می‌کند. شاخهٔ پایدار هرگز برگشت نمی‌خورد.
- **مقایسه.** `GET …/splits/:id/report?from&to&version` دو شاخه را مقایسه می‌کند: تعداد درخواست،
  خطا و نرخ خطا، میانگین و p95 تأخیر، میانگین زمان تا اولین توکن، توکن‌ها و هزینهٔ کل و میانگین، از
  لاگ درخواست (`policy.split`).

پاسخ‌ها هدر `x-dirouter-split: <id>; v=<version>; branch=<stable|canary>` دارند؛ نام مدلی که مشتری
می‌بیند همان است که فرستاده.

| متد و مسیر                                                                          | مجوز           |
| ----------------------------------------------------------------------------------- | -------------- |
| `GET /orgs/:orgId/routing/splits` و `GET …/:id/versions`                            | `models:read`  |
| `POST /orgs/:orgId/routing/splits` و `PATCH`/`DELETE …/:id` و `POST …/:id/rollback` | `models:write` |
| `GET /orgs/:orgId/routing/splits/:id/report`                                        | `usage:read`   |

## ۳. ترافیک سایه (کارت ۳۲.۴)

سیاست سایه نمونه‌ای (`sampleRate`، ۰ تا ۱) از درخواست‌های یک نام (`match`، یا `*` برای همه، و در
صورت نیاز فقط یک `projectId`) را به مدل `target` هم می‌فرستد تا مدل تازه روی ترافیک واقعی سنجیده شود
بی‌آنکه کسی متوجه شود.

- **بی‌اثر روی مشتری.** نسخهٔ سایه فقط بعد از اینکه مشتری کل پاسخش را گرفت (stream تمام شد)، جدا از
  درخواست، به‌صورت غیر stream و با timeout خودش (`timeoutMs`، پیش‌فرض ۶۰ ثانیه) شروع می‌شود. به
  محدودیت نرخ و سقف همزمانی کلید، بودجه‌ها، کیف پول، bulkhead ارائه‌دهنده، breakerها، آمار مسیریابی،
  کش‌ها و ضبط بدنه دست نمی‌زند، پس مدل سایهٔ کند یا خراب هیچ چیزی را که مشتری می‌بیند تغییر نمی‌دهد.
  هر replica حداکثر ۳۲ نسخهٔ همزمان اجرا می‌کند و بقیه را کنار می‌گذارد؛ هر خطایی بلعیده می‌شود.
- **چه کسی می‌پردازد.** مقصد باید یکی از مدل‌های **خود** سازمان (یا alias یا combo آن‌ها) باشد:
  سازمان هزینهٔ آزمایش خودش را به ارائه‌دهندهٔ خودش می‌پردازد. مدل عمومی marketplace هنگام ذخیره رد و
  در گیت‌وی نادیده گرفته می‌شود. از مشتری چیزی گرفته نمی‌شود (`chargeUsd` صفر)، از کیف پول چیزی رزرو
  یا کم نمی‌شود و هزینه هرگز در بودجهٔ کلید، پروژه یا تیم حساب نمی‌شود.
- **ثبت جدا.** هر نسخه یک رویداد مصرف با فیلد `shadow` است (`requestId` برابر `<primary>:shadow`).
  worker آن را فقط در `shadow_requests` می‌نویسد، نه در `request_log`، دفتر کل، تجمیع ساعتی و روزانه
  یا کیف پول؛ پس مصرف، فاکتور و بودجه‌ها تغییری نمی‌کنند. فقط سازمان مالک می‌تواند آن را بخواند.
- **بودجهٔ جدا.** `dailyBudgetUsd` هزینهٔ هر سیاست را در هر روز UTC محدود می‌کند (شمارندهٔ Valkey
  `dirouter:shadow:spend:<policy>:<day>`)؛ با رسیدن به سقف تا روز بعد متوقف می‌شود. اگر شمارنده خوانده
  نشود نسخهٔ سایه فرستاده نمی‌شود.
- **مقایسه.** `GET …/shadows/:id/report?from&to` پاسخ سایه و اصلی را مقایسه می‌کند: خطا، میانگین و
  p95 تأخیر و هزینه، به‌همراه هزینهٔ سایهٔ امروز در برابر سقف.

| متد و مسیر                                                   | مجوز           |
| ------------------------------------------------------------ | -------------- |
| `GET /orgs/:orgId/routing/shadows`                           | `models:read`  |
| `POST /orgs/:orgId/routing/shadows` و `PATCH`/`DELETE …/:id` | `models:write` |
| `GET /orgs/:orgId/routing/shadows/:id/report`                | `usage:read`   |
